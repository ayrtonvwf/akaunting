# Audit

Where this fork stands before anything is changed. Ch1 of the plan in
[`specs/northstar/PLAN.md`](specs/northstar/PLAN.md).

Measured on 2026-08-12. Generated evidence lives in `audit-out/` and is regenerated by the scripts in
`tools/audit/`; this document is written on top of it.

## 1. Runtime and framework position

*Provenance: hand-verified, one source per claim.*

| | declared | supported until | status |
|---|---|---|---|
| PHP | `^8.1` | 31 Dec 2025, end of life | unsupported for 7 months; last release was 8.1.34 |
| Laravel | `^10.0` | 4 February 2025, last security fix | unsupported for 18 months; bug fixes ended 6 August 2024 |

Sources:

- PHP supported versions: https://www.php.net/supported-versions.php (8.1 is no longer listed there;
  its end-of-life date is on https://www.php.net/eol.php)
- Laravel support policy: https://laravel.com/docs/releases#support-policy

Note that `php: ^8.1` already permits installing on 8.4; the constraint is a floor, not a ceiling.
What it does mean is that 8.1-only idioms are still legal in this codebase, which is what Ch3 Half A
raises.

Two further dates from the same two sources, for scale. The PHP release in active support today is
8.4, whose own active support runs to 31 Dec 2026 and security support to 31 Dec 2028. The current
Laravel major is 13, released 17 March 2026; Laravel 12, this audit's target, is itself already past
its bug-fix date of 13 August 2026 and carries security fixes only until 24 February 2027.

## 2. The CI gap

*Provenance: read from `.github/workflows/tests.yml`.*

- The test matrix is `['8.1', '8.2', '8.3']`. The supported PHP release is 8.4, so the runtime the
  project should be running on is the one runtime CI never exercises. The bottom of the matrix, 8.1,
  has been end-of-life since December 2025.
- Every lane sets `coverage: none`. No coverage data is produced anywhere today, which is why Ch1's
  map needed a local instrumented run and why producing coverage in CI is a Ch2 deliverable.
- A nightly soak lane exists (added by this fork, not upstream) and runs the suite 20 times on 8.3 to
  hunt flakes. It is gated to `workflow_dispatch` and the nightly `schedule`, not to pushes and pull
  requests, and it too sets `coverage: none`.

Four readings of that table that are easy to get wrong:

- **`abandoned` takes precedence over `ceiling-below` in the classifier.** `intervention/imagecache`
  has a ceiling of 10 — as low as anything here — but classifies `abandoned`, so it does not appear
  in the `ceiling-below` count. The two `ceiling-below` rows are `akaunting/laravel-menu`
  (first-party, ceiling 10) and `lorisleiva/laravel-search-string` (ceiling 10).
- **`supports-12` means "ceiling at or above 12", not "the latest release runs on 12".**
  `staudenmeir/belongs-to-through` (latest v2.18) and `staudenmeir/eloquent-has-many-deep` (latest
  v1.22.1) both classify `supports-12` with ceiling 13, but their latest releases declare
  `illuminate/database: ^13.0` and nothing lower — they cannot install on Laravel 12 at all. On
  Laravel 12 these two need an older release than the one the table calls latest. This is a trap in
  the table's own vocabulary, not an error in the data.
- **`ceilings.php` scans `require`, not `conflict`.** `nunomaduro/collision` is `framework-agnostic`
  in the table because its locked v7.12.0 declares no `laravel/framework` or `illuminate/*`
  requirement — but it does declare `conflict: laravel/framework >=11.0.0`. It is the only direct
  package in the 57 with such a conflict. It is recorded in the declared-versus-actual list below,
  which is what that list is for.
- **`laravel/framework`'s latest upstream stable is v13.25.0, released 2026-08-11.** This fork
  installs 10.50.2 and this audit targets 12. The gap is one major wider than the chapter's own
  target admits.

The plan in `specs/northstar/PLAN.md` records twelve first-party `akaunting/*` packages. There are
**13**: the eleven `akaunting/laravel-*` entries plus `akaunting/module-offline-payments` and
`akaunting/module-paypal-standard`. Correcting the count, not carrying it forward.

### Declared versus actual

The table above records what each package *declares*. The resolver probes in
`audit-out/probe-l11.txt` and `audit-out/probe-l12.txt` record what Composer *does* when asked to
move. Neither probe resolves. Both produce eight `Problem` blocks — identical apart from the target
major — in which `laravel/framework` is available at the requested version but seven currently locked
direct packages are not moved by a probe that names only `laravel/framework`, and their locked
versions cap out below 11. The Laravel 12 transcript additionally carries a
`composer why-not laravel/framework 12` cross-check, which names 19 further direct packages and 17
transitive-only ones — counting distinct names in that transcript, and setting aside
`laravel/framework` itself, the root package, and the `illuminate/*` subsplits that appear there as
requirement targets rather than as packages of their own.

Where table and probe disagree, both readings are kept:

- `akaunting/laravel-firewall` — table says `supports-12` (ceiling 13), probe blocks the move,
  because the locked 2.3.0 requires `laravel/framework ^9.0|^10.0|^11.0|^12.0` and the probe does not
  move it.
- `akaunting/laravel-language` — table says `supports-12` (ceiling 12), probe blocks, because locked
  1.0.22 is well behind its own latest 2.0.0.
- `akaunting/laravel-mutable-observer` — table says `supports-12` (ceiling 12), probe blocks, because
  locked 2.0.1 requires `laravel/framework ^9.0|^10.0`.
- `akaunting/laravel-setting` — table says `supports-12` (ceiling 13), probe blocks, because locked
  1.2.9 is not moved.
- `akaunting/laravel-sortable` — table says `supports-12` (ceiling 13), probe blocks, because locked
  2.0.2 requires `laravel/framework ^9.0|^10.0`.
- `akaunting/laravel-version` — table says `supports-12` (ceiling 13), probe blocks, because locked
  1.0.4 is not moved.
- `santigarcor/laratrust` — table says `supports-12` (ceiling 13), probe blocks, because locked 7.2.1
  requires `laravel/framework ~6.0|~7.0|~8.0|^9.0|^10.0`.
- `akaunting/laravel-money`, `barryvdh/laravel-dompdf`, `barryvdh/laravel-ide-helper`,
  `beyondcode/laravel-dump-server`, `graham-campbell/markdown`, `laravel/sanctum`,
  `laravel/slack-notification-channel`, `plank/laravel-mediable`, `wnx/laravel-stats` — table says
  `supports-12`, the `why-not` cross-check names each of them, because each is locked at a version
  whose `illuminate/*` range stops at `^10` or `^11`.
- `staudenmeir/belongs-to-through` and `staudenmeir/eloquent-has-many-deep` — table says
  `supports-12` (ceiling 13), the probe names both, because their locked versions require
  `illuminate/database ^10.0`. This is a second, tighter constraint on top of the latest-release
  problem noted above: at latest they need `^13.0`, at locked they need `^10.0`, and Laravel 12 sits
  between the two.
- `nunomaduro/collision` — table says `framework-agnostic`, the `why-not` output says
  `v7.12.0 conflicts laravel/framework (>=11.0.0)`, because `ceilings.php` reads `require` and not
  `conflict`. The only such case in the 57.

The table's two `ceiling-below` packages are both named by the probes, so that category shows no
disagreement: `akaunting/laravel-menu` (locked v3.1.2 requiring `illuminate/config|support|view
^9.0|^10.0`) and `lorisleiva/laravel-search-string` (locked v1.3.0 requiring
`illuminate/support ^9.0|^10.0`).

The probe output is also the only source for the third kind of blocker the plan asks about: a
transitive dependency holding a direct one back. Those are named here:

- `genealabs/laravel-pivot-events` (locked 10.0.1, requiring `illuminate/database|support
  ^8.0|^9.0|^10.0`) holds back `genealabs/laravel-model-caching`, whose own row reads ceiling 13.
  The ceiling reflects that package's latest release only; this dependency is invisible to
  `ceilings.json` and is a separate cap.
- `staudenmeir/eloquent-has-many-deep-contracts` (locked v1.1, requiring `illuminate/database
  ^10.0`) holds back `staudenmeir/eloquent-has-many-deep`, independently of that package's own
  latest-release constraint.
- `laravelcollective/html` (locked v6.4.1, requiring `illuminate/http|routing|session|support|view
  ^6.0|^7.0|^8.0|^9.0|^10.0`) holds back `akaunting/laravel-menu`, reinforcing its `ceiling-below`
  row rather than contradicting it.
- `laravel/prompts` (locked v0.1.25; `laravel/framework` v12.0.0 requires `^0.3.0`) holds back

- In the same self-referential category: `nesbot/carbon`, `nunomaduro/termwind` and ten `symfony/*`
  sub-packages are `laravel/framework`'s own requirements, needed at newer versions by v12.0.0 than

## 4. The coverage map

*Provenance: generated by `tools/audit/coverage-map.php` from a single instrumented local run.*

Produced with PCOV in the local Docker image, running the suite serially rather than in parallel:

    docker compose -f compose.local.yml run --rm --no-deps app php -d pcov.enabled=1 -d pcov.directory=/var/www/html/app -d memory_limit=-1 vendor/bin/phpunit --coverage-clover audit-out/clover.xml

Overall: 12,070 of 26,935 statements, 44.81%, across 1,062 files.

Two axes over the same run. Surface is the leading path segment under `app/`, with `Http/` split so
that `Http/Middleware` and `Http/Controllers` are separate — middleware is upgrade-sensitive in a way
controllers are not. Domain is the first segment matching the product areas in `docs/product/`;
everything else is `cross-cutting`, and that bucket's size is reported so it cannot absorb the
codebase unnoticed. There are 31 surface buckets and 9 domain buckets; `cross-cutting` holds 502 of
the 1,062 files.

The untested-file column is the more useful one for choosing what Ch2 writes first. A percentage is a
headline; a count of files with zero covered statements is a worklist.

The baseline moved because of this fork's own Ch0 work, not because upstream added tests. Both rows
are kept rather than one replacing the other. The plan's figures were correct when measured on
2026-08-05 and are stale now; anything downstream of this document should use the 2026-08-12 row.

Counting rules, since different rules give different numbers: a test file is any `*Test.php` under
`tests/`; a test method is a `function testX` declaration or a `#[Test]`/`@test` marker; an assertion
call is any `->assertSomething(`. The assertion figure moved furthest of the three, which is a
consequence of the counting rule as much as of new tests.
